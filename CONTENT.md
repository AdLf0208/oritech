# Oritech — content carry

`assets/` and `data/` at the package root are generated by
[`tools/carry_content.py`](tools/carry_content.py) from the ATM10 jar
`oritech-neoforge-1.21.1-1.2.13.jar`
(SHA-256 `32600bf5b08fcf6d4a49e557f90ee45b238098170777872c8919d9fdb0a1b828`).
The script is deterministic (`--check` exits 1 on any drift) and writes **81
files** at the root; since 0.2.0 they travel in the same SDK package as `src/`,
so there is no separate content `.hmod` and no manifest here (the root
`horizon-mod.toml` is the only one).

## Carried byte for byte from the jar (40 files)

| File | Why |
|---|---|
| `assets/oritech/textures/block/models/{basic_generator_block,pulverizer_block,powered_furnace_block}.png` | each machine's own texture from its GeckoLib model |
| `assets/oritech/{blockstates,models/block,models/item}/machine_core_N.json` (N = 1..7) | the cores' vanilla models, which the jar already has |
| `assets/oritech/textures/block/machine_core_N.png` (N = 1..7) | the cores' textures |

`machine_core_hidden` is upstream's worldgen plating, not part of the multiblock, and is not carried.

## The jar's pulverizer recipes, with the 26.3 ingredient form (7 files)

`data/oritech/recipe/pulverizer/{bone,blaze,dripstone,glowstoneore,coalore,diamondore,lapisore}.json`
are the jar's files whose input and output both exist in this slice. A 1.21.1 file writes its
ingredient as an object (`{"item": …}` / `{"tag": …}`), which 26.3's loader refuses — the recipe is
dropped at load and can never craft. The script rewrites **only** the ingredient list to the bare form
(`"minecraft:bone"`, `"#minecraft:coal_ores"`); type, results and time stay the jar's. `notes.md` →
*Carry defect fixed* has the evidence; in game, all seven are crafted in `tools/e2e.sh` phase O.

The other 117 files under `data/oritech/recipe/pulverizer/` name Oritech dusts, clumps and gems that
are not carried here; they are a later slice (see `notes.md`, gaps).

## Deviations from the jar's data

1. **The machine block models.** The jar's blockstates point at
   `oritech:block/machine_speed_addon` (a placeholder: GeckoLib draws the real
   machine from `assets/oritech/geo/block/models/*.geo.json`, which the pin
   cannot render). This slice maps each machine's **own texture** onto a
   `cube_all`, so the block is visible and distinct without a GeckoLib renderer.
   The models and the machine's block item are what look different; the block's
   collision, hardness, resistance, sounds and tool are the jar's.
2. **No `facing` state.** Upstream's machine blocks carry
   `HORIZONTAL_FACING`; this slice declares no state property, because nothing
   renders or uses the orientation here (every face accepts items and energy).
3. **No `lit` state on the powered furnace.** Upstream switches `LIT` (and light
   level 15) while it works; with a `cube_all` model and no light support in the
   carried declaration the state has nothing to drive, so it is a recorded gap.
4. **No `core_used`/`machine_assembled` blockstates.** Upstream marks a used core
   and an assembled controller on the block; this slice keeps the assembly in
   the controller's saved compound and re-checks the core each tick (see
   `notes.md` → *Deviations (slice 2)*).
5. **Loot shape.** Upstream's 1.21.1 `conditions: [ … ]` array evaluates false
   at this pin; the carried loot uses 26.3's `condition: { … }` object. Same
   entry, same `survives_explosion` rule.
6. **No crafting recipes for the nine blocks.** The jar's recipes need
   `oritech:motor`, `oritech:magnetic_coil` and the `c:ingots/nickel`,
   `c:storage_blocks/copper` and `c:player_workstations/furnaces` tags, none of
   which exist in this slice or in 26.3's vanilla data. Shipping them would ship
   recipes that can never match, so they are recorded as a gap instead.
7. **The creative tab is the machines tab only.** The jar registers four
   (`itemgroup.oritech.machines|components|decorative|equipment`); this slice has
   items for one (nine blocks).
