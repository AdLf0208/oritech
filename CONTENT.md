# Oritech — content carry

`assets/` and `data/` at the package root are generated by
[`tools/carry_content.py`](tools/carry_content.py) from the ATM10 jar
`oritech-neoforge-1.21.1-1.2.13.jar`
(SHA-256 `32600bf5b08fcf6d4a49e557f90ee45b238098170777872c8919d9fdb0a1b828`).
The script is deterministic (`--check` exits 1 on any drift) and writes **276
files** at the root; since 0.2.0 they travel in the same SDK package as `src/`,
so there is no separate content `.hmod` and no manifest here (the root
`horizon-mod.toml` is the only one).

## Carried byte for byte from the jar (55 files)

| File | Why |
|---|---|
| `assets/oritech/textures/block/models/{basic_generator_block,pulverizer_block,powered_furnace_block,cooler_block,lava_generator_block}.png` | each machine's own texture from its GeckoLib model |
| `assets/oritech/{blockstates,models/block,models/item}/machine_core_N.json` (N = 1..7) | the cores' vanilla models, which the jar already has |
| `assets/oritech/textures/block/machine_core_N.png` (N = 1..7) | the cores' textures |
| `assets/oritech/models/{block,item}/machine_{speed,efficiency,ultimate,processing,capacitor,burst}_addon.json` | slice 5: the six addons' own vanilla block and item models |
| `assets/oritech/textures/block/machine_{speed,efficiency,ultimate,processing,capacitor,burst}_addon_off.png` | slice 5: their `_off` textures (the same look upstream has before an addon is claimed) |
| `assets/oritech/models/{block,item}/machine_redstone_addon.json` and `assets/oritech/textures/block/machine_redstone_addon_off.png` | slice 6: the Control Unit Addon's own model and texture (its `_on`/`_powered` models are not carried — one blockstate variant) |
| `assets/oritech/textures/block/machine_particle_texture.png` | slice 5: the particle texture every addon model names |

`machine_core_hidden` is upstream's worldgen plating, not part of the multiblock, and is not carried.

## Slice 7: the items, the plating blocks, the tags and the recipes (82 files)

**Carried byte for byte** (`ITEM_ASSETS`, `PLATING_ASSETS`): the seven items' item models and textures
(`assets/oritech/{models/item,textures/item}/{steel_ingot,nickel_ingot,electrum_ingot,raw_silicon,silicon,magnetic_coil,motor}`),
and the three plating blocks' block model, item model and their `particle` texture
(`assets/oritech/{models/block,models/item}/…plate…` and `assets/oritech/textures/block/<block>/particle.png`;
the jar's other four CTM textures belong to its `athena:ctm` blockstate, which this pin has no loader
for).

**Authored**: each item's 26.3 item definition (`assets/oritech/items/<item>.json`), its declaration
(`data/oritech/horizon/item/<item>.json`, `template: minecraft:iron_ingot`), its lang name
(`item.oritech.<item>`); each plating block's one-variant blockstate, item definition, block
declaration (the `minecraft:iron_block` copy, opaque), self-drop loot table, lang name
(`block.oritech.<block>` — the jar's "… Reinforced Plating") and place in the machines tab; the
`components` creative tab (`ItemGroups.COMPONENT_GROUP`); and the **fourteen tags** the recipes name:

| Tag | Values | Source |
|---|---|---|
| `c:ingots/steel`, `c:ingots/nickel`, `c:ingots/electrum` | the one Oritech ingot each | authored from the declarations (the jar's own files repeat `steel_ingot` twice and name `biosteel_ingot`, which this package does not carry) |
| `c:ingots/{iron,copper,gold}` | `minecraft:{iron,copper,gold}_ingot` | the conventional tags NeoForge generates for vanilla items; 26.3 ships no `c:` namespace |
| `c:dusts/{redstone,quartz}` | `minecraft:redstone`, `minecraft:quartz` | same |
| `c:gems/{diamond,lapis}` | `minecraft:diamond`, `minecraft:lapis_lazuli` | same |
| `c:silicon` | `oritech:silicon` | the jar's own file's content |
| `c:storage_blocks/copper` | `minecraft:copper_block` | conventional |
| `c:player_workstations/furnaces` | furnace, blast furnace, smoker | conventional |
| `oritech:plating` | the three plating blocks carried | the jar's tag without the carbon plating (the centrifuge's carbon fibre) |

**The eighteen recipes** (`CHAIN_RECIPES`) are the jar's files in the bare ingredient form 26.3 loads:
`crafting/alloy/{steel,electrum,rawsilicon}`, `crafting/magnet`, `motor/motorcraft`, `crafting/{plating,iron,nickel}`,
`crafting/{basicgen,pulverizer,electricfurnace,cooler,lavagen}`, `crafting/{core1,core2,core3alt}`,
`crafting/addon/redstone` and `silicon_from_smelting_raw_silicon`. The rewrite touches the shaped
`key`, the shapeless `ingredients` and the smelting `ingredient` only; results, counts, patterns, times
and `experience` are the jar's. A *list* ingredient is refused by the tool (26.3 drops such a file).
## Slice 8: the Assembler, the adamant ingot and the assembler recipes (18 files)

**Carried byte for byte**: the assembler block's own texture
(`assets/oritech/textures/block/models/assembler_block.png` — its blockstate names the
`machine_speed_addon` placeholder and its item model is `builtin/entity`, so both are authored here),
and the adamant ingot's item model and texture
(`assets/oritech/models/item/adamant_ingot.json`, `assets/oritech/textures/item/adamant_ingot.png`).

**Authored**: the assembler's one-variant blockstate and `cube_all` block model, its item model
(`{parent: oritech:block/assembler_block}`), its 26.3 item definition, its block declaration (the
`minecraft:iron_block` copy with `occludes: false`, like the other machines), its self-drop loot table,
its lang name (`block.oritech.assembler_block` → "Assembler"), its place in the machines tab and the
pickaxe / stone-tool tags; the adamant ingot's 26.3 definition, `horizon/item` declaration
(`minecraft:iron_ingot`) and lang name, and its place in the components tab.

**Recipes**: the five `data/oritech/recipe/assembler/*.json` whose ingredients *and* result resolve
(`motor`, `magnet`, `blazerod`, `fireball`, `shroomlight`), plus `crafting/alloy/adamant.json` and
`crafting/assembleralt.json` — each the jar's file with only the bare-ingredient rewrite, and each
crafted in game (`notes.md` → *Slice 8*). The other 52 assembler files are refused one reason per
family in *The recipe set* there.

Which files were taken and which left, with a reason each, is `notes.md` → *Slice 7* → *The recipe
table*.

**Recipes**: `pulverizer/coal.json` (`#minecraft:coals` → coal dust), `centrifuge/carbon.json`

## The jar's pulverizer, chiller and lava generator recipes (10 files)

`data/oritech/recipe/pulverizer/{bone,blaze,dripstone,glowstoneore,coalore,diamondore,lapisore}.json`
are the jar's files whose input and output both exist in this slice. A 1.21.1 file writes its
ingredient as an object (`{"item": …}` / `{"tag": …}`), which 26.3's loader refuses — the recipe is
dropped at load and can never craft. The script rewrites **only** the ingredient list to the bare form
(`"minecraft:bone"`, `"#minecraft:coal_ores"`); type, results and time stay the jar's. `notes.md` →
*Carry defect fixed* has the evidence; in game, all seven are crafted in `tools/e2e.sh` phase O.

`data/oritech/recipe/cooler/{ice,obsidian}.json` (slice 3) are the chiller's two recipes whose fluid
and result both exist here: `minecraft:water` → 3 ice and `minecraft:lava` → 2 obsidian, 200 ticks
each. Their `fluidInput` and `results` are the jar's; only the (empty) ingredient list is rewritten.
The third, `snow.json`, takes `oritech:still_steam` — a fluid this package does not declare — so it is
not carried (`notes.md`, gap).

`data/oritech/recipe/lavagen/lava.json` (slice 4) is the lava generator's one recipe this package can
run: 100 mB of `minecraft:lava` for 120 ticks, with no item input and no item result. Its
`sheolfire.json` takes `oritech:still_sheol_fire` — another fluid this package does not declare — so
it is not carried (the same recorded gap as `snow.json`).

The other 117 pulverizer files (the coal one is slice 9's), and the other 60 assembler / the 91 of 93
centrifuge / 29 foundry / 32 refinery recipes, name Oritech dusts, clumps, gems and fluids that are not
carried here; they are a later slice (see `notes.md`, gaps).

## Deviations from the jar's data

1. **The machine block models.** The jar's blockstates point at
   `oritech:block/machine_speed_addon` (a placeholder: GeckoLib draws the real
   machine from `assets/oritech/geo/block/models/*.geo.json`, which the pin
   cannot render). This slice maps each machine's **own texture** onto a
   `cube_all`, so the block is visible and distinct without a GeckoLib renderer.
   The models and the machine's block item are what look different; the block's
   collision, hardness, resistance, sounds and tool are the jar's.
2. **No `facing` state.** Upstream's machine blocks carry
   `HORIZONTAL_FACING`; this slice declares no state property, because nothing
   renders or uses the orientation here (every face accepts items and energy).
3. **No `lit` state on the powered furnace.** Upstream switches `LIT` (and light
   level 15) while it works; with a `cube_all` model and no light support in the
   carried declaration the state has nothing to drive, so it is a recorded gap.
4. **No `core_used`/`machine_assembled` blockstates.** Upstream marks a used core
   and an assembled controller on the block; this slice keeps the assembly in
   the controller's saved compound and re-checks the core each tick (see
   `notes.md` → *Deviations (slice 2)*).
5. **Loot shape.** Upstream's 1.21.1 `conditions: [ … ]` array evaluates false
   at this pin; the carried loot uses 26.3's `condition: { … }` object. Same
   entry, same `survives_explosion` rule.
6. **~~No crafting recipes for the nineteen blocks.~~ Closed by slice 7.** The
   components (`oritech:motor`, `oritech:magnetic_coil`, the plating blocks, the
   ingots) and the conventional `c:` tags those recipes name are carried now, so
   all five machines, three machine cores and the Control Unit Addon are
   craftable at a table (`notes.md` → *Slice 7*). The ingots' *ore* is the one
   remaining gap: the pin cannot generate a content package's configured
   features (`blocked(configured-feature-not-registered)`).
7. **Two creative tabs.** The jar registers four
   (`itemgroup.oritech.machines|components|decorative|equipment`); this package
   has items for two — the machines (twenty-two blocks) and the components
   (seven items).
8. **The addons' blockstate is authored.** The jar's `machine_*_addon.json`
   blockstates have 24 variants keyed by `face`/`facing`/`addon_used`, states
   upstream's `FaceAttachedHorizontalDirectionalBlock` carries; this port declares
   a plain block (no `ADDON_USED`, no addon block entity — see `notes.md` →
   *Deviations (slice 5)*), so the blockstate is one `""` variant pointing at the
   carried `_off` model. The Control Unit Addon (slice 6) is the same shape, and
   its jar `powered` state is not declared either (it would only choose between
   `_on` and `_powered` models the port does not carry).
